## 2. Análisis archivo por archivo

### 2.1 `joz/backend/joz/apps.py` (+11 / −0)

**Qué cambia.** Añade `def ready()` a `JozConfig` que, vía import perezoso, llama `iniciar_scheduler()` desde `joz/scheduler.py`. Incluye guarda contra doble inicio bajo `runserver --autoreload` (chequea `RUN_MAIN`) y try/except para no romper el startup si el import falla. Es el hook que arranca APScheduler con el ETL programado.

**Riesgo de adoptar.**

- **Dependencia oculta**: `from joz.scheduler import iniciar_scheduler`. El archivo `joz/backend/joz/scheduler.py` **existe en disco pero está untracked en git**. Si se adopta `apps.py` sin versionar también `scheduler.py`, un clone fresco verá `apps.py` importando un módulo que no existe → arranca pero ignora silenciosamente la falla por el try/except. Funciona, pero queda incoherente.
- **Dependencia de runtime**: requiere `APScheduler>=3.10`, que está justamente en el item 2.4 de este análisis.
- **Comportamiento por defecto seguro**: `iniciar_scheduler()` chequea `ETL_SCHEDULER_ENABLED` env (default off). Hoy el contenedor productivo tiene `ETL_SCHEDULER_DISABLED=true` y no setea la otra; el scheduler **no arranca** aunque adoptemos esto. Adopción "safe-by-config".
- **Side effect cuando se reactive el ETL**: cuando alguien setee `ETL_SCHEDULER_ENABLED=true`, este hook arrancará el cron diario 03:00. Esto coincide con la fase próxima de IA + embeddings documentada en §13 del v2.1.

**Riesgo de descartar.** Pierde el hook de arranque automático. Cuando se decida reactivar el ETL, habrá que reescribirlo (trivial, 10 líneas). No se pierde nada de `scheduler.py` (sigue en disco).

**Recomendación.** **Adoptar — pero condicionado a versionar también `joz/backend/joz/scheduler.py` y agregar `APScheduler` a `requirements.txt`** en el mismo commit. Las tres piezas se tienen que tocar juntas, sino queda un import roto en silencio. El doc v2.1 §3.4 ya menciona "`apps.py: Hook de arranque del scheduler`" — adoptarlo es honrar la documentación entregada.

### 2.2 `joz/backend/joz/etl.py` (+5 / −3)

**Qué cambia.** En `_cargar_movimientos`, cambia el filtro de deduplicación. Antes consultaba "transacciones existentes con fecha = `fecha_consulta`"; ahora arma un set con los IDs del payload (`ids_entrantes`) y consulta "transacciones existentes con `id_externo` en ese set". Es decir, el filtro deja de depender de la fecha del query y se vuelve un lookup por IDs.

**Riesgo de adoptar.**

- **Más robusto contra duplicados cross-fecha**. Si SuperEfectivo devolviera un mismo `id_externo` en dos llamadas con fechas distintas (raro, pero el API ya nos sorprendió antes con fechas mutables), el código viejo intentaría reinsertar y la `UniqueConstraint(id_externo)` de la migración 0006 abortaría la inserción contando un error. El cambio lo evita en la query previa.
- **Performance neutral**. `id_externo__in=<lista de ~hasta 1000>` con index único es eficiente.
- **ETL deshabilitado hoy**. Este código no corre en producción mientras el endpoint `/etl/run/` responde "ETL deshabilitado". Riesgo en runtime = 0 hasta la reactivación.

**Riesgo de descartar.** Mantiene el comportamiento actual (filtrar por fecha exacta + dejar que el upsert lo maneje vía constraint). No es buggy, sólo menos defensivo. Se pierde una mejora chica de robustez que costó 5 líneas.

**Recomendación.** **Adoptar.** Mejora defensiva pequeña sobre código que actualmente no corre. Cero riesgo, pequeño beneficio cuando se reactive el ETL.

### 2.3 `joz/backend/joz/management/commands/seed_joz.py` (+1,084 / −84)

**Qué cambia.** Reemplazo casi total del seeder. Versión actual (committeada): 116 líneas que cargan **244 transacciones reales** extraídas del PDF de SuperEfectivo (las únicas que hubo durante la integración). Versión del stash: 1,084 líneas que generan **~7,000 transacciones sintéticas** simulando un año fiscal completo, con nombres panameños realistas, descripciones de joyas, aperturas/cierres de caja, traslados, Western Union, etc. Al final del seed corre dos pasos adicionales: `_run_detection` (genera alertas con sus propios umbrales hardcoded) y `_run_risk_calculation` (genera riesgos con su propia fórmula).

**Riesgo de adoptar.**

- 🚨 **CRÍTICO — reintroduce una fórmula de riesgo paralela.** `_run_risk_calculation` en el stash usa `score = pct_volumen*0.3 + tasa_alerta*0.4 + min(tasa_critica*5, 1)*0.3` con umbrales `tasa_critica ≥ 0.15 alto / ≥ 0.05 medio`. Esto **contradice** la fórmula que dejamos como fuente única en `backend/joz/riesgos.py` (`min(tasa*10,1)*0.4 + (avg_score/100)*0.3 + min(tasa_crit*20,1)*0.3`, umbrales 0.55 score / 0.03 tasa_crit). Adoptar este seed re-introduce la divergencia que el Bloque B unificó.
- 🚨 **CRÍTICO — reintroduce constantes de detección hardcoded.** SEED_ZSCORE_MEDIA=2.0, SEED_FRACC_MIN_TXNS=5, SEED_CAJERO_RATIO=2.0. La detección debería leer parámetros de `ReglaDeteccion.parametros`, no constantes paralelas en el seed.
- **Borraría las 244 transacciones reales del seed actual** si alguien corre `seed_joz` sobre BD limpia. Esas 244 son los únicos datos auténticos del cliente disponibles.
- **Sin dependencias nuevas en runtime** (`random` y `math` son stdlib).
- **Comando manual**: NO corre automáticamente en rebuild. Sólo si alguien invoca explícitamente `python manage.py seed_joz`. El "blast radius" del cambio es bajo en operación normal — sólo afecta entornos donde alguien quiera (re)sembrar la BD.

**Riesgo de descartar.** Se pierden 1,084 líneas de trabajo de Cristhiam: nombres panameños, descripciones de joyas, simulación de WU, traslados, intereses. Útil para demos sin datos del cliente, para entornos de QA, para tests de carga.

**Recomendación.** **Consultar con Cristhiam.** El valor del seeder sintético es real para demos y dev, pero el motor de detección + cálculo de riesgo embebidos contradicen la arquitectura unificada que entregamos. La pregunta concreta es: ¿quiere mantenerlo si lo refactorizamos para que **delegue** en `detectar_anomalias` y `calcular_riesgos` en lugar de implementarlos en paralelo? Si dice sí, adoptamos modificado. Si dice no, descartamos.
