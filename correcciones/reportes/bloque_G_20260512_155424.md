- `docker exec barranquia_joz_backend python manage.py check` → **System check identified no issues**. (El contenedor sigue corriendo la imagen pre-G porque no se hizo rebuild, así que este check no valida el código nuevo en runtime — pero confirma que el modelo está sano y que las migraciones aplicadas son consistentes.)
- `apps.py:ready()` invoca `from joz.scheduler import iniciar_scheduler` envuelto en try/except, con guarda `RUN_MAIN` para evitar arrancar dos veces bajo `runserver --autoreload`.
- `scheduler.py:iniciar_scheduler()` chequea el env **antes** de importar `apscheduler.*`, de modo que el contenedor productivo (sin `APScheduler` instalado todavía) ejecuta el hook, lee el env, sale con `return`, y nunca toca el import → arranque limpio aunque la imagen sea pre-G.

### Observación documental (no se corrige en este bloque)

`scheduler.py` respeta la env **`ETL_SCHEDULER_ENABLED`** (opt-in). El doc v2.1 §11.1 documenta **`ETL_SCHEDULER_DISABLED`** (opt-out). Son dos variables distintas. Comportamiento neto sigue siendo seguro (default off por opt-in del código + el contenedor productivo tiene `ETL_SCHEDULER_DISABLED=true` por las dudas), pero la divergencia documental existe y conviene reconciliarla en un bloque futuro — sea ajustando el código para que use el nombre del doc, sea actualizando el doc para que refleje la realidad del código.
